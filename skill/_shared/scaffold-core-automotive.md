# 车机承载内核（HarmonyOS 智能座舱目标端）

**定位**：Phase 3/4 在车机端"落壳与验收"的公共事实基座。本文件只写两类内容：(1) 从华为官方座舱文档确认的形态规则与能力；(2) 未能在官方文档确认、但影响验收的点，一律标 `PENDING_CONFIRM`，禁止当事实用。官方口径以「智能座舱 2.0」文档中心（ICS-v2）与《智能座舱-针对多设备设计》设计指南为准。

## Non-negotiable

- 继承 `controller-core.md` 四阶段治理与核心等价契约；车机端**交互范式允许且通常必须重设计**（桌面→座舱），但行为语义（意图/数据/计算/状态/结果/持久化/副作用）不许漂移。
- **驾驶安全约束是验收标准的一等公民**，不是可选项：遮挡避让、行车状态管控、最小交互、音频焦点四类断言进入 Gate 3 蓝图与 Gate 4 验收（见下文"安全约束规约"）。
- 未经官方文档确认的车机 API/工具名禁止写进工单；标 `PENDING_CONFIRM` 的事实只能作为调研项，不能作为 Gate 判定依据。
- 模拟器/实车不可得时，行车状态类断言降级为 GAP + SOURCE_CONFIRM 并明示降级路径；禁止用手机模拟器截图冒充车机形态验证（可以做降级演示，但必须标注"降级演示"）。

## 车机承载模型（从官方文档确认）

- **屏幕拓扑**：座舱由一块或多块屏构成（中控屏、仪表、HUD、副驾屏等）。**生态/第三方应用的默认落点是中控屏**；仪表显示有专门能力（场景化方案含"中控信息仪表投屏""仪表显示和图层叠加"，多为系统侧能力，第三方应用能否直接上仪表 `PENDING_CONFIRM`）。落屏裁决必须在 Gate 1 冻结：默认中控，其他屏逐项裁决并记 PLATFORM_DEVIATION 候选。
- **一级界面框架 = 分栏结构**：官方设计指南规定全屏一级界面采用通栏 / 二分栏（A+B）/ 三分栏（A+B+C）结构，**常用重要功能放左侧分栏**（驾驶位左手侧优先级最高）。桌面端的菜单栏/工具栏/侧边树应映射到左分栏 A，而不是照搬桌面布局。
- **多窗交互三态**：应用需支持全屏、2/3 屏、1/3 屏三种窗口尺寸；布局可分别参考平板、折叠机（分栏）、手机竖屏三种形态；官方推荐支持无级调节。对应 ArkUI 落地：`GridRow`/`GridCol` 断点体系 + 窗口尺寸监听（`@ohos.window`）组合，禁止把某一比例写死。
- **多窗三态与断点形态的映射规约**（把"参考三种形态"落成可判定口径）：全屏 → 车机标准分栏形态（A+B/A+B+C）；2/3 屏 → 折叠机类分栏形态（左分栏保留、内容区收窄）；1/3 屏 → 手机竖屏类单列形态（分栏收起为抽屉/入口列表）。每态布局进 breakpoint_plan 同款三字段声明（窗态 × 布局形态 + 承载组件），断点判定基于应用窗口宽度（与 tablet 内核断点体系同源）。
- **导航分屏**：9 英寸以下屏幕不支持分屏；常规矩形屏导航与其他应用左右 1:2 分屏（窗口宽高比约 9:5）；竖屏/较小屏 1:1。迁移源端"MDI 多文档/多窗口平铺"类功能时优先映射到分屏/多窗三态，而不是多窗口。
- **影音规则**：单张图片内容高度不超过屏幕 1/2；视频按比例居中，不得拉伸或截断。行车中视频播放限制属"驾驶安全管控"范畴（具体策略 `PENDING_CONFIRM`，按官方"驾驶安全管控"场景化方案核对）。
- **观视与交互模型**：人眼与座舱屏物理距离约 60-70cm（约为手机/平板两倍）；驾驶时是"双任务并行"，用户**瞥视而非持续注视**；交互入口是多模态的（语音、方向盘按键、旋钮、硬按键、触控、手势）。这构成"最小交互"验收的物理依据：字号/触控目标显著大于桌面/手机规范，操作步骤与注视时长要短。

## 语音优先与多模态交互（驾驶态的替代通道规范）

- **多模态入口清单（官方设计指南确认）**：语音、方向盘按键、旋钮、硬按键、触控、手势——蓝图的交互重映射表必须把桌面输入逐类映射到其中之一或组合，"仅触控"的车机化方案默认不通过审阅。
- **语音优先原则**：驾驶态（行车中）被管控或高注视成本的功能，安全替代通道优先排序为 ①语音 ②停车后继续 ③简化触控；"语音替代"进入 minimal_interaction_map 时只登记**语义意图**（用户要达成什么），不绑定具体语音技能实现。
- **第三方应用的语音能力接入**（应用内意图/小艺类语音助手集成）：开放 API 与接入方式 `PENDING_CONFIRM`（以 ICS-v2 文档区核对），未核实前蓝图只写"语音替代通道声明"，不写实现承诺。
- **方向盘按键/旋钮映射**：硬件按键事件对第三方应用的开放度 `PENDING_CONFIRM`；模拟器上无法注入硬件按键的操作降级为触控路径重放 + 声明（操作通道重映射，结果断言不变）。

## 安全约束规约（进入蓝图与验收的四类断言）

1. **遮挡（occlusion）**：方向盘可能遮挡部分屏幕（典型为驾驶位左下区域），关键信息与重要操作必须避开遮挡区。验收断言：核心控件边界不落入冻结的遮挡矩形（遮挡区坐标随模拟器/实车屏幕规格冻结，模拟器上无真实方向盘时按设计指南默认区标注并声明来源）。
2. **行车状态管控（driving-state）**：官方场景化方案"驾驶安全管控"支持**按不同行车状态管控不同屏幕上应用的状态**。验收断言：列入管控清单的功能（如行车中视频、长文本录入）在行车态被禁用/降级/给出安全替代（语音或停车后继续），静止态行为与源端语义等价。行车状态注入方式：官方工具专区提供"模拟电源状态信号（Mock 注入）"等工具；行车工况（车速/挡位）注入 API `PENDING_CONFIRM`，不可得时该类断言降级为 GAP。
3. **最小交互（minimal-interaction）**：桌面端深菜单/多步向导迁到车机必须做交互范式重设计（合并步骤、左分栏直达、语音替代、大目标单手可达），但行为语义等价（同意图、同结果断言）。验收断言：重设计后的操作序列逐步记录为 harmony_steps，行为契约的结果断言不变；交互步数不劣于冻结的门槛（Gate 1 按 feature 裁决）。
4. **焦点/多音区（audio-focus）**：座舱多音区提供音频焦点、音量管理、音频路由策略。迁移源端"提示音/后台播放/多路音频"类功能时，验收断言：后台播放类申请音频焦点的行为符合座舱路由策略（具体 API 以 ICS-v2「座舱多音区」文档为准 `PENDING_CONFIRM`）；无音频 feature 的应用声明"不占用焦点"。

## 行车场景分级与管控清单口径

- **场景两态起步**：静止（P 挡/驻车）与行车（行驶中）为本体系最低验收集；细分状态（低速/高速/充电中）只在官方"驾驶安全管控"方案确认可注入后再纳入（注入手段 `PENDING_CONFIRM`，见安全约束规约第 2 条）。
- **管控清单的圈定依据**（按 feature 裁决，Gate 1 冻结）：涉及长注视（视频/长文本阅读）、双手占用（键盘录入/精密拖拽）、高认知负荷（多步向导）的功能默认入清单；仅语音反馈/短瞥可读的功能默认不受控。清单理由逐条留痕，禁止整 app 一刀切禁用（那是拒绝迁移，不是安全适配）。
- **两态行为断言模板**：静止态=与源端语义等价（标准四维差分）；行车态=禁用（入口不可达且给出替代提示）/降级（只读或精简）/替代（语音通道达成同意图）三选一，且所选处置与 driving_state_policy 一致——不一致即 FORM_FACTOR 级 FAIL（安全断言差）。
- **两态断言的证据形态**：静止态走标准取证链（dumpLayout/截图/探针）；行车态取证绑定行车态注入证据（官方 Mock 工具输出），无注入证据的"行车态已验证"结论一律不成立（防伪口径，同 controller-core 真实性铁律）。
- **生态对照提示**：AAOS 的 DO（Distraction Optimized）分级可作圈定参考（哪些功能类型该入清单的行业经验），但两态断言的判定以 ICS-v2 口径书写，禁止把 AAOS 条款直接写进鸿蒙验收标准。

## 多屏与仪表能力边界（落屏裁决的事实基座）

- **中控屏（默认）**：生态应用标准落点，本内核组件规约全部按中控屏书写。
- **仪表/HUD**：官方场景化方案含"中控信息仪表投屏""仪表显示和图层叠加"，定位为系统侧能力；第三方应用直接渲染上仪表 `PENDING_CONFIRM`——涉及仪表的 feature 一律进 PLATFORM_DEVIATION 候选，不建壳。
- **副驾屏/后排屏**：多屏设备上的分屏与独立显示能力以 ICS-v2 多屏多窗口文档为准（逐项 `PENDING_CONFIRM`）；默认 run 只承诺中控，其他屏为增强项。
- **跨屏一致性**：同一 feature 多屏展示时行为契约共享（同一语义对象与结果断言），渲染差异按视觉还原口径单独验收，不算行为 DIFF。

## Gate 3 车机特化判定（在 controller-core 判据上叠加，机器可查）

- ① **safety 节四字段非空**：每个用户可见 surface 的 occlusion_policy / driving_state_policy / minimal_interaction_map / audio_focus_claim 齐备（缺任一 FAIL，与 tablet 内核 breakpoint_plan 三字段同强度）。
- ② **窗态三字段非空**：涉多窗承载的 surface 有全屏/2/3/1/3 三态布局声明（见"多窗三态与断点形态映射"节）。
- ③ **多模态映射声明存在**：交互重映射表覆盖源端全部输入类，驾驶态替代通道含语音/停车后/简化触控至少其一。
- ④ 原有四条基线判定（承载面覆盖/数据契约无孤儿/冒烟链/环境链）照常。
- 模拟器降级 run：①③照常查（蓝图层可验），②④中依赖座舱环境的证据项按降级策略显式标注 GAP 后不计 FAIL——降级标注本身缺失才是 FAIL。

## 组件规约（车机版原生优先 + 与 phone 内核的分叉映射策略）

- 原生优先清单沿用 ArkUI：`Navigation`+`NavPathStack`（路由）、`Tabs`、`List`+`LazyForEach`、`CustomDialog`/`bindSheet`（模态）、系统返回。车机特化：分栏承载优先 `SideBarContainer`（左分栏 A + 内容区 B/C）或 `GridRow` 断点组合；禁止自绘导航栈/自造弹层底盘（与 android 版 R1-R6 静态检查同口径）。
- **与 scaffold-core-phone 的分叉映射表**（phone 范式 → 车机特化）：

| phone 内核范式 | 车机端分叉 | 依据 |
|---|---|---|
| Navigation Stack 单栏为主 | 全屏默认二/三分栏（SideBarContainer / GridRow 组合），单栏仅 1/3 窗态 | 一级界面=分栏（设计指南） |
| 底栏 `Tabs` 多页范式 | 左分栏 A 直达入口替代底栏；确需多页用顶部/侧向页签并登记理由 | 常用功能左侧分栏优先 |
| 模态向导多步弹层 | `bindSheet` 分步或左分栏内分步；深向导必须重设计合并步骤 | 最小交互断言 |
| 手机字号/触控目标规范 | 字号与目标显著放大（60-70cm 瞻视距离）；具体数值标准 `PENDING_CONFIRM` 以官方 UX 指南为准 | 视距/双任务模型 |
| 列表项滑动操作/长按菜单 | 大目标按钮 + 更多按钮；手势保留为辅助 | 驾驶态触控可靠性 |
| 快捷键体系 | 方向盘按键/语音映射声明（开放度 `PENDING_CONFIRM`，仅登记） | 多模态入口 |

- 桌面→车机映射基线：菜单栏/工具栏→左分栏 A；状态栏/托盘→车机状态区或去除（托盘类 feature 记 PLATFORM_DEVIATION 候选）；模态向导→`bindSheet` 分步或左分栏内分步；右键上下文菜单→长按/更多按钮（触屏范式）；快捷键→方向盘按键/语音（仅声明映射，能力 `PENDING_CONFIRM`）。
- 分叉映射表的判定口径：表中"phone 范式 → 车机特化"是**默认裁决**，不是禁令——确有 feature 需保留 phone 范式（如副驾娱乐屏的底栏多页）时，在蓝图 notes 登记理由并经人工批准；但"字号/触控目标放大"与"安全四断言"两行不允许豁免。
- 深浅模式：智选车特性含深浅模式，蓝图必须冻结双模式下的可读性（与源端主题能力对齐）。

## 环境与工具（真实性口径）

- **座舱模拟器**：DevEco Studio 已上线「鸿蒙座舱模拟器」，系统版本 HarmonyOS 7.0.0 (26.0.0) Beta1，17.2 英寸车机屏、3402×1620、432dpi（2026-06 HDC 前后发布；多家媒体交叉确认，DevEco Studio 官方 Release Notes 原文 `PENDING_CONFIRM`）。节奏：2026-06 开发者 Beta → 2026-09 实车 Beta → 2026-12 商用。使用前必须在 run 环境冻结里记录实际可得的 DevEco 版本与模拟器规格；**不可得时按下文降级，禁止假装可得**。
- **官方座舱工具链**（ICS-v2 工具专区）：获取窗口状态信息、scrcpy 录屏、音频抓流、模拟电源状态信号（Mock 注入）。行车工况注入、遮挡区官方标注工具 `PENDING_CONFIRM`。
- **通用命令链**：DevEco Studio 构建 HAP；`hdc install` / `hdc shell aa start` 安装启动；`hdc shell snapshot_display` 截图；`hdc shell uitest dumpLayout` 组件树 dump（以本地 DevEco/hdc 版本实测为准）。可执行文件路径双平台对照总表见 `skills/_shared/00-CONVENTIONS.md`。
- **降级策略（模拟器不可得时，按序尝试并如实记录）**：① DevEco 手机/平板模拟器 + 分栏布局代码层断言（GridRow 断点、SideBarContainer 结构）——只能验证布局规约，不能验证车机形态；② Previewer 预览 3402×1620 画幅（自定义画幅支持度 `PENDING_CONFIRM`）；③ 人工评审录屏。降级期间行车状态/遮挡/焦点三类断言全部记 GAP，不参与 PASS 判定。
- **降级级别标注格式**：降级 run 的每份形态类证据头部标注 `DEGRADED:<level>`（level ∈ phone_emu / previewer / manual_video），Gate 报告汇总降级面；无标注的车机截图按"伪冒充"处理（与手机截图冒充车机验证同罪）。
